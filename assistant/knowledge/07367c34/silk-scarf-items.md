## The ten recipes and declared bonuses

## Details and qualifications (each traced; read the lines)
**Black Belt.** `totalDamage` is `physicalDamage + specialDamage + trueDamage`, rounded, computed **before** `handleDamage` runs (`pokemon-state.ts:236–238`), so it is **pre-defense and pre-shield**: the target's DEF/SPE_DEF, shields, redirects and kills do not reduce it. It already includes the crit multiplier on the physical/special part (`:215–216`) and any Nullify PP damage. The effect runs from `onAttack`, which the code calls for every basic attack, **successful or not** (`pokemon-entity.ts:910, 938–950`; `pokemon-state.ts:284–296`). `crit` is the crit roll itself, so against Rocky Helmet (which sets the crit reduction factor to 0, `:67–70`) the crit still counts for the Belt. A dodged/protected attack sets `damage = 0` (`:99–117`), so the shield is `ceil(0.33 × 0)` plus whatever special damage was added (e.g. Nullify) — usually 0. The shield passes through `addShield`, so Big Eater Belt scales it if also held.

**Explosive Band.** Trigger: `OnShieldDepletedEffect` is fired from two places — damage that meets or exceeds the current shield (`pokemon-state.ts:620–643`) and a negative `addShield` that takes the shield to ≤ 0 (`:408–417`). It only fires if the shield was > 0 in the damage path. On firing it removes the item (so **once**), then hits every adjacent (8-cell) **enemy** with `handleSpecialDamage` (`getAdjacentCells`, `board.ts:152–163`). **Amount:** `round(0.5 × dps.shield)` where `dps` is the holder's entry in the team's DPS meter (`blueDpsMeter`/`redDpsMeter`). That `shield` field is **not** "shield the holder received": `Dps.shield` is copied once per simulation tick from the entity's `shieldDone` (`simulation.ts:1345–1384`, `dps.ts`), and `shieldDone` is incremented only in `addShield` as `caster.shieldDone += shield` for positive shields **given by that caster** (`pokemon-state.ts:407`). So it counts shield the holder has **granted** (to itself or others; self-granted ones include the item's own bonus shield, applied through `addShield(value, this, …)` at `pokemon-entity.ts:1425–1427`), and **not** shield granted to the holder by other units. It lags by up to one tick. If the entry is missing, the damage is 0.

**Big Eater Belt and Twist Band — supported methods.** Both helper functions are applied inside `PokemonEntity` methods (`pokemon-entity.ts:1839–1868`). Big Eater Belt (×1.25, `roundToNDigits(…, "down")`, only when the value is positive, or negative from a same-team caster, i.e. a buff being lost) is applied in 11 methods, at these lines: `addShield` 504, `addCritChance` 546, `addCritPower` 571 (2 digits), `addMaxHP` 587, `addDodgeChance` 615 (3 digits), `addAbilityPower` 636, `addLuck` 662, `addDefense` 688, `addSpecialDefense` 714, `addAttack` 740, `addSpeed` 759. It is **not** applied in `addPP`. Twist Band (flips a negative value to positive when the caster is the environment or an enemy) is applied in 11 methods: `addPP` 521, `addCritChance` 547, `addCritPower` 572, `addMaxHP` 588, `addDodgeChance` 616, `addAbilityPower` 637, `addLuck` 663, `addDefense` 689, `addSpecialDefense` 715, `addAttack` 741, `addSpeed` 760; it is **not** applied in `addShield`. Where both apply, the Belt runs first. Not covered by either: damage, healing, status conditions (burn, freeze, …), range, and anything that changes stats without these methods. Consequences: the Belt's own HP 50 and SHIELD 15 are scaled by itself (held items are copied into the fight entity before `applyItemsEffects` applies them, `pokemon-entity.ts:163–165`, `simulation.ts:498–534`), giving 62 and 18 by the rounding rule (inference from the code, not executed). Separately, several stat-**stealing** abilities wrap the steal in a `target.items.has(TWIST_BAND) === false` guard, so a Twist Band victim is not stolen from (I read the guard lines, not each ability's full body: `spectral-thief.ts:38`, `bared-fangs.ts:24`, `high-jump-kick.ts:18`, `heart-swap.ts:24`, `steel-wing.ts:39`, `electro-web.ts:28`, and, for the thief's gain only, the HP-swap wand `effects/synergies.ts:624`).

**Cover Band.** In `handleDamage`, after damage reduction and shield absorption have **already been applied to the original target**, if `target.hp − residualDamage ≤ 0` and the target does **not** hold Cover Band, the code looks among the 8 adjacent cells for a same-team unit with Cover Band and `hp > 0` (`pokemon-state.ts:698–725`). If found, it **returns** `coverAlly.handleDamage({ damage: incomingDamage … })` — the cover ally takes the **original, unreduced** incoming damage, which runs the full pipeline again with the **cover ally's** defenses and shield; its HP can drop to 0. Qualifications: the original target keeps the shield loss and effects already applied before the redirect (e.g. Explosive Band can fire), but loses no HP and gains no damage-PP from that hit; only the first matching adjacent holder is used; units that themselves hold Cover Band are not covered; it triggers only on a **lethal** hit, not on non-lethal ones; whether a non-adjacent ally is covered after movement depends on positions at the moment of the hit.

**Efficient Bandanna.** At simulation start (`simulation.ts:239–262`) it visits `x−1, x, x+1` on the holder's row (`effects/items.ts:1536–1548`) and sets `maxPP = round(0.85 × maxPP)` for **any entity found on those cells, with no team check** (`getEntityOnCell`, `board.ts:33–37`; off-board cells return nothing). The holder is included. Two holders covering the same unit stack multiplicatively (each rounds). Its own `PP 15` bonus adds to current PP only. Whether an enemy can stand on those cells at the start was not examined.

**Nullify Bandanna.** (1) `canCast` is false while held (`pokemon-entity.ts:250–256`), and attack/moving states cast only when `pp ≥ maxPP && canCast` (`attacking-state.ts:92`, `moving-state.ts:40–43`), so the unit **never casts**. (2) In the basic-attack calculation, `specialDamage += pokemon.pp; pokemon.pp = 0` (`pokemon-state.ts:132–135`): PP is **spent** on each basic attack, one-for-one as extra raw special damage (then rounded and run through the target's SPE_DEF and shields like other special damage, `:257–268`, and it adds to `totalDamage`). The attack's own +5 PP (`ON_ATTACK_MANA`, `config/game/battle.ts`) is added afterwards in `onAttack`, so the next attack carries at least that. Damage taken adds PP (`ceil(residual/10)`) between attacks. (3) `addAbilityPower` returns early: the unit gains **Attack = round(0.2 × value)** instead of AP and **ignores the AP boost and crit factors** (`pokemon-entity.ts:621–631`); this applies to any `addAbilityPower` call, positive or negative, and the item's own AP bonuses (none declared for it) are unaffected. Counting: it uses 2 scarf slots of the Normal-synergy allowance (below).

## Scarf allowance vs crafting (correction)
Normal synergy tier (thresholds 3/5/7/9, `config/game/synergies.ts:180`; tier = number of thresholds reached, `synergies.ts:300–307`) is the number of scarf items the **player's Normal synergy supports** (`player.ts:504–570`, `getScarvesItemsWithNbScarves`, where Nullify Bandanna counts as 2).
- `player.scarvesItems` **tracks** which crafted scarf results are part of that allowance. The crafting code (`game-commands.ts:670–678` inventory combine; `:906–932` combine on a unit) **pushes the result to `scarvesItems` only if `scarvesItems.length < Normal tier`**; the craft itself — creating the item and consuming the components (`:681–683`) or `pokemon.addItem` (`:932`) — **does not depend on that check**. An over-limit craft therefore still succeeds, it is just not tracked.
- Tracking matters when the Normal tier **drops**: `updateScarves` then removes the lost tracked scarves, first from a holder on the board, otherwise from the inventory (`player.ts:542–564`); untracked crafted scarves are not touched by that removal. (Earlier text in this session that read `game-commands.ts:908–916` as a cap on crafting was wrong.)
- Scarves are excluded from random item rewards (`CraftableItemsNoScarves`, e.g. `pve-stages.ts`); sources seen: Normal-tier grants (`player.ts:533–541`), the gift shop and the Cinccino encounter (`gift-shop.ts:273`, `mini-game.ts:580–587`). Not fully traced.
