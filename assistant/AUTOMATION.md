## What exists
| File | Role |
|---|---|
| `automation/inventory.json` (derived) | every ability and passive identifier in the saved catalog (540 abilities, 193 passives), the units that use it, how the pinned source routes it (registry → class → file; `PassiveEffects` entry or other references), implementation groups/families, **routing uncertainties**, and the current structured coverage. Regenerate with `node assistant/automation/inventory.mjs`; `--check` verifies it is current. |
| `automation/queue.json` (state) | one record per identifier not yet fully covered: stable id (`ability/NAME`, `passive/NAME`), revision, units still to cover, dependencies, priority (= units affected), uncertainty codes, blockers, and **separate** work / validation / review state. One record per line. |
| `automation/review-status.json` (human) | independent review status of existing records. Workers never edit it. |
| `candidates/07367c34/` | generated candidate records. Never read by lookups, `ASK.md` or `match-reference.md`. `review-followups.md` there records outstanding review findings on candidates that stay pending (read it before touching one of them). |
| `automation/queue.mjs`, `inventory.mjs`, `branch-guard.mjs`, `ensure-source.mjs`, `record-checks.mjs` | the tools (Node only, no install). `record-checks.mjs` is deliberately not under a `lib/` directory because the root `.gitignore` ignores directories named `lib`. |
| `automation/test-automation.mjs` | fixture tests; `--verbose` prints the demonstration. |

**Three states are never merged:** *work* (queued · in_progress · candidate_ready · blocked · superseded), *validation* (not_run · passed · failed — mechanical checks only) and *review* (none · pending · reviewed — human only). A candidate that passed validation is `candidate_ready` with review `pending`; it is **not** reviewed knowledge and is never promoted by a run.

## Candidate format
```json
{ "schema": 1, "label": "production-branch reference; deployment unverified", "sourceSha": "07367c341fe928763da2b565c2eee010433e4fc1",
  "itemId": "ability/NAME", "kind": "ability", "identifier": "NAME", "reviewStatus": "candidate",
  "generatedBy": { "runId": "<RUN>" }, "record": { … } }
```
`record` mirrors a record of `data/07367c34/reusable-abilities.json`: **ability** — `ability, label, sourceSha, appliesTo[{key,stars,maxPP,range,declaredSkill,declaredPassive}], dispatch, summary, targeting, geometry, effects[{kind,declaredRaw,scaling,resolution,evidence[ids]}], statusEffects, starBehavior, positionalConditions, repeatedCastsAndModes, rawVsResolved, sourceTables, numericExamples (optional), dependsOnUnverifiedGenericCombat, unresolved, evidence[{id,file,lines,symbol,expect,note}]`; **passive** — `passive, label, sourceSha, appliesTo, kind, summary, trigger(s), effects, conditions, resetBehaviour, dependsOnUnverifiedGenericCombat, unresolved, evidence` (a record may also use `sourceEvidence`/`unitEvidence` objects with `"evidence": [ids]` to cite). Rules: `appliesTo` must equal the queued `units` exactly; every evidence id must be used and every used id defined; `expect` is a text snippet that really occurs in the cited lines (whitespace-insensitive); every numeric table written in the source gets a `sourceTables` entry `{id, file, pattern (one capture group of comma-separated numbers), recordPath, unitValuesPath?}`; raw declared amounts are labelled raw, and where a stat helper, held item or clamp can change them the record says requested vs applied; routing uncertainties from the queue record that matter go into `unresolved`; units sharing the identifier but not listed are **not** covered. No gameplay claims.

## Validation (shared, not bespoke)
`automation/record-checks.mjs` performs, for every ability / passive / gap record: revision and label; required fields (a stricter profile for candidates); unit bindings (stars, maxPP, range, skill, passive against `catalog-units.json`, plus the unit's class block in `pokemon.ts`); evidence references (file readable at the pinned revision, line range exists, `expect` present, ids resolve, no orphan ids for candidates); declarative numeric tables (`sourceTables`, including per-unit values at the unit's stars); numeric examples of **registered** kinds (`specialAfterSpeDef`, `tableAtStars`, `sum`; add a kind once in the library, not per ability). `validate-abilities.mjs` keeps all its earlier bespoke checks and additionally runs these shared checks on all nine existing records.

### Semantic claims that stay unchecked
Mechanical checks cannot establish: that a summary, targeting or scaling sentence is true; that an `expect` snippet supports the sentence citing it (it only proves the text exists there); that no other caller, helper, item, synergy or status changes the behaviour (completeness); that example kinds without a registered formula are right; behaviour in a real fight (no probe, no gameplay evidence); that units sharing an identifier behave alike beyond the listed ones. These need independent human review. `queue.mjs validate` reports how many such categories remain.

## Resumption, ownership, limits
- A fresh run reads `queue.json` only: `in_progress` records are offered first (resume), `blocked` ones are skipped, `candidate_ready` ones wait for review. `sync` merges a regenerated inventory without touching progress.
- **One writer.** The lock in `queue.json` is committed and pushed first; a second run either fails to take it (fresh lock, exit 4), or fails to push (exit 3). A lock older than 180 minutes may be taken over (logged). No parallel sessions, no subagents.
- **Bounded by record count**: at most five records per run (the tool refuses a sixth); two repair attempts per record. This does **not** enforce an account-credit or token limit; nothing here measures or guarantees cost or response time.
- **Branch safety**: `branch-guard.mjs` refuses default branches, verifies that `origin/<branch>` is still the commit the run started from, that all changes are under `assistant/`, and pushes without force. If the branch moved: stop and report.
